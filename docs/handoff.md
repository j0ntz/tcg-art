# Orchestration handoff (v2)

The orch is a task -> reviewed-deliverable engine handling **code, repo docs, and board-ops**, on a 6-state machine, forking on PR-presence. **Design source of truth: `docs/orch-v2-spec.md`.** This file is the operational entry point: what's live, the flow, the hard-won gotchas (§3), and the file map (§4). Also read `CLAUDE.md` (repo conventions).

## 1. What's live (on `main`)

Autonomous loop on the Claude Max subscription (no API billing). State lives in GitHub Projects board "Agent Orchestration" (project #1, user `j0ntz`) in the single-select **Agent Status** field. launchd cron `com.tcg-art.orch` @60s runs `orchestration/tick.sh`.

- **6 states:** Pending -> Running -> Verifying -> Verified -> Landing -> Done. The gerund stages (Running / Verifying / Landing) carry a live tmux session; **Verified** is the one human gate (`auto-land` bypasses it); **Done** is terminal. `blocked` is a **label** on the current state (so you see WHERE it stuck), NOT a state.
- **Path fork (PR-presence):** repo-bound (the work opened a PR) -> Verified -> Landing -> Done. No-PR (research-only findings / board-ops) -> Done directly.
- **Labels:** flavor `research` / `design` / `instructions` / `chore` (absent = code), `auto-land` (skip the Verified gate, fully hands-off), `blocked` (stuck-flag), `parent` (umbrella task with sub-issue children; visibility only, the orch gates on the native links).
- **Parent/child tasks (GitHub sub-issues):** multi-deliverable work fans into child tasks that are NORMAL board tasks (own item/state/branch/PR); the parent waits in **Pending** behind `watch.sh`'s `children_gate` until every child is complete (issue closed or board Done), then rides normally for its fan-in (integration or a summary comment; PR-presence fork applies). All link reads/writes are REST (zero GraphQL). Design + rationale: `docs/orch-subtasks-design.md`.
- **Per-task model + effort:** the **Agent Model** (Fable 5 / Opus 4.8 / Opus 4.7 / Sonnet 5 / Sonnet 4.6) and **Agent Effort** (low / medium / high / xhigh / max; the label IS the CLI value) board single-selects set what the task's spawned agents START on; unset = `agent.defaultModel` / `agent.defaultEffort` in config ("" = no flag). Mirrors the Edge orch's Asana `agent_model` / `agent_effort` fields. Maps + field/option ids live in `orch.config.json` `agent`; `spawn_agent` resolves via `model_for` / `effort_for` from the tick snapshot (zero extra GraphQL). Set in the board UI or `board.sh model <n> "<label>"` / `board.sh effort <n> <level>`. A human can still flip a LIVE session per-turn via the RC/desktop picker.
- **Skills** (`.claude/skills/`, repo-local): `work-task` (build/write/ops + address review threads), `verify-code` (preview-test + independent PR review), `verify-doc` (completeness + independent review), `land-task` (semantic-resolution merge), `validate-block` (true-blocker validator), `draft-task` (front door). Spawned via `claude --dangerously-skip-permissions "/<skill> <issue-url>"` in tmux. Remote Control is attached only for stages in `agent.remoteControlStages` (default `["work"]`): each RC spawn adds a claude.ai session + one notification, so the churny verify/land stages stay off it and are observed via their artifacts (PR review, run report, tick.log) or tmux attach.
- **Handlers** (`orchestration/`): `tick.sh` = rate-limit guardrail -> fetch board once -> `watchdog.sh` + `watch.sh` (Pending) + `verify.sh` (Verifying) + `land.sh` (Landing).
- **Vercel:** account `jontz` (linked to `j0ntz` GitHub), project `tcg-art`, protection DISABLED (public previews). `verify-preview.sh <pr#> "<expected>"` resolves the preview via the GitHub Deployments API and headless-Chrome captures it (desktop + true-mobile).
- **Config:** `orchestration/orch.config.json` (+ `lib.sh` loader). Board ids, Vercel scope, merge method (squash), worktrees root, concurrency -- all swappable here.

## 2. The flow

Each handler acts on ONE task per tick, is idempotent via a tmux session presence-guard, and **skips any task carrying `blocked`**.

- **Pending** -(watch.sh)-> Running -(`/work-task`)-> the work agent does the job by flavor (code: implement + build gate + PR; doc: research/write the doc(s) + PR; ops/`chore`: operate on the board, usually no PR) OR, on re-entry, addresses the open review threads -> sets **Verifying**. watch.sh scans Pending in board order and spawns the first ELIGIBLE task: `blocked` skipped, a parent held until `children_gate` says every child is complete (`[watch] #n parent waiting (k/t ...)` in the tick log).
- **Verifying** -(verify.sh -> `/verify-code` for code, `/verify-doc` for doc/ops)-> a FRESH agent verifies (code: preview-test then cold PR review; doc/ops: completeness + soundness). **Binary verdict:** any change requests -> **Pending** (the watch handler re-spawns work-task, which sees the open review threads and enters address mode; routing to Running would strand the task, no handler spawns for it -- bit issue #13); clean + open PR -> **Verified**; clean + no PR -> **Done**.
- **Verified** -("you", or `auto-land`)-> **Landing** -(land.sh)-> squash-merge (or `/land-task` for semantic conflict resolution) -> **Done**.
- **blocked** label: every agent runs `/validate-block` before flagging it; the task stays in its state for you to investigate, clear, and re-queue.

**Human touchpoints only:** create the task (`/draft-task`); `Verified -> Landing` (unless `auto-land`). Everything else is the orch.

**Follow-up feedback (pre-land):** just comment what you want on the ISSUE, no prefix (works from GitHub mobile), then move the task back to **Pending** (board UI drag or `board.sh status <n> Pending`). The convention is inverted: ORCH comments carry an HTML marker (`<!-- orch -->` / `<!-- address-round -->` / `<!-- review-task -->`, enforced in the skills, the run-report template, watchdog.sh and land.sh); any UNMARKED comment is human feedback. A feedback comment is consumed when it carries the orch's +1 reaction (the receipt), so "latest" is exact: unmarked + un-reacted = new; when directives conflict the newest comment wins. The work agent acts on each, +1-reacts it, and lists it in its round summary; the verifier fails the round if any went unconsumed. Fresh feedback resets the 2-round address cap (the cap only stops verifier ping-pong). Variant selection in multi-branch tasks is the same move: comment "promote option B (PR #<x>) to the primary branch, close the others". Post-land (Done) there is no reopen: follow-up = a new `/draft-task`.

**Sessions:** `claude-work-<n>`, `claude-verify-<n>`, `claude-land-<n>`. The watchdog maps each active state to its session: frozen -> kill (Running also -> `blocked`; Verifying/Landing re-spawn), Running with a dead session -> `blocked`, and it retires any stale session whose state has moved on.

## 3. Gotchas (hard-won -- these WILL bite if unknown)

- **Skill names must be unique.** The global `slash-command-detection` rule (`~/.claude/CLAUDE.md`, from `~/.cursor/rules`) hardcodes "/word -> read `~/.cursor/skills/<word>/SKILL.md`". The repo `CLAUDE.md` overrides to prefer repo-local, but reuse a name that exists in `~/.cursor/skills` (e.g. `pr-review`, `pr-address`, `one-shot`) and you risk the Edge skill loading instead. That is why the skills are `work-task` / `verify-code` / `verify-doc`, not `im` / `pr-review`.
- **Spawn flag is `--dangerously-skip-permissions`**, not `--yolo` (doesn't exist in this claude version).
- **Worktrees go in `~/git/.tcg-art-worktrees`**, NOT `~/git/.agent-worktrees` -- the Edge watchdog GCs the latter and will delete them mid-run. Sessions named `claude-{work,verify,land}-*` so the Edge watchdog (which only manages `claude-asana-*`) ignores them.
- **Spawn agents with cwd INSIDE the repo/worktree** (`cd` first) or `.claude/` skills are not discovered. `lib.sh`'s `spawn_agent` does this.
- **Editing the Projects single-select field's options via the API RECREATES all option IDs and clears existing items' statuses.** Snapshot item statuses + option IDs first, then restore (the v1->v2 6-state migration did exactly this). The recreate is all-or-nothing, so rename ALL options you want in one shot.
- **GraphQL budget is account-wide, Projects is GraphQL-only, a board read is ~31 pts** (of 5000/hr). Hence fetch-once (`ORCH_BOARD_SNAPSHOT`) + the `rate_limit` reserve guardrail in `tick.sh`. The `gh api rate_limit` endpoint is FREE. External board polling during a run can starve the agents -- prefer tailing the (free) tick log. This applies to `board.sh` too: every standalone call re-reads the whole board, so BATCH operations (queueing several tasks, setting status+model+effort across issues) must fetch once and share it: `export ORCH_BOARD_SNAPSHOT=$(mktemp); gh project item-list 1 --owner j0ntz --format json --limit 200 > "$ORCH_BOARD_SNAPSHOT"`, then run the `board.sh` calls. Burning the budget mid-queue strands half-configured tasks until the hourly reset (happened 2026-07-02).
- **`sfw` wrapper:** bare `npm`/`npx`/`yarn` are blocked -- prefix with `sfw`. The `sfw` hook also rejects a heredoc containing the literal word "npm" -- write such files (PR/issue/review bodies) with the editor, not `cat <<EOF`.
- **launchctl** may need the user's GUI session; if `install-watcher.sh install` fails from a headless context, run it from a Terminal.
- **launchd hands the job a BARE environment** (no `HOME`, `PATH=/usr/bin:/bin:/usr/sbin:/sbin`). `lib.sh`'s `$HOME/...` paths and node (nvm-managed on some Macs) then fail with `node: command not found` + `board fetch failed` every tick, while a manual `bash tick.sh` works fine. `install-watcher.sh` bakes `HOME` + node's dir into the plist `EnvironmentVariables`; re-run it if node moves. `orchestration/doctor.sh` catches this and every other prerequisite; full setup is `docs/bring-up.md`.
- **Mergeability race:** never force-push then immediately `gh pr merge` (GitHub returns mergeable=UNKNOWN and the merge fails). Use GitHub's computed mergeability (`gh pr view --json mergeable,mergeStateStatus`) -- the lander already does.
- **Sub-issues API:** `sub_issue_id` in the REST calls is the issue's int64 `id`, NOT its number (`board.sh add-child` handles the lookup). `sub_issues_summary` on the parent payload is eventually consistent AND counts only CLOSED children (a no-PR child goes board-Done with its issue open) -- never gate on it; `children_gate` reads the `/sub_issues` list + board snapshot instead. `gh` has no native sub-issue commands (as of 2.93.0); it's all `gh api`.

## 4. File map + how to operate

- `orchestration/`: `lib.sh` (config loader + `board_items_json` + label helpers + `first_item_in_state` / `ensure_worktree` / `spawn_agent` with `ORCH_DRY_RUN` + sub-issue helpers `sub_issues_json` / `parent_of` / `children_gate`), `board.sh` (board read/write + `has-label`/`add-label`/`remove-label` + `children`/`parent`/`gate`/`add-child`), `tick.sh` (guardrail + fetch-once + handlers), `watch.sh`, `verify.sh`, `land.sh`, `watchdog.sh`, `verify-preview.sh`, `screenshot-mobile.mjs`, `install-watcher.sh`, `doctor.sh` (preflight), `bootstrap.sh` (one-command bring-up), `orch.config.json`, `templates/run-report.md`.
- `.claude/skills/`: `work-task/`, `verify-code/`, `verify-doc/`, `land-task/`, `validate-block/`, `draft-task/`.
- **Design:** `docs/orch-v2-spec.md`. **Fresh machine:** `docs/bring-up.md` (clone + `orchestration/bootstrap.sh`); `orchestration/doctor.sh` to diagnose.
- **Queue a task:** `/draft-task <intent>`, or by hand: open an issue in `j0ntz/tcg-art`, add it to project #1, `board.sh status <n> Pending`, apply the flavor label(s) + `auto-land` if it should merge hands-off. Optionally pin model/effort: `board.sh model <n> "<label>"`, `board.sh effort <n> <level>`. Multi-deliverable intent: `/draft-task` splits it into a parent + child sub-issues (link by hand with `board.sh add-child <parent#> <child#>`).
- **Watch:** `tail ~/.config/tcg-orch/tick.log`, or the board at https://github.com/users/j0ntz/projects/1.
- **Stop the cron:** `orchestration/install-watcher.sh uninstall`.

## 5. Open follow-ups

- **Harder validator enforcement:** a project `PreToolUse` hook gating the `blocked` label (like Edge's `require-concession-validation.sh`), instead of the current soft "agent must call `/validate-block`".
- **Retry cap on handler-agent crashes:** Verifying/Landing re-spawn indefinitely if the agent keeps dying; add a per-issue per-state attempt counter -> `blocked` after N.
- **Board view for `blocked`:** since it's a label now, add a filtered/colored view so stuck tasks are visible at a glance (the status grouping no longer has a Blocked column).
- Clean-path land skips re-verify-after-rebase (add a config flag if you want it).
